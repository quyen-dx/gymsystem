# ADR-013: Remove Session Model — RefreshToken as Single Auth State

- **Status:** Accepted
- **Date:** 2026-07-20
- **Deciders:** Technical Lead, Documentation Architect
- **Supersedes:** None
- **Related:** ADR-003 (JWT Bearer Tokens over Session-Based Auth)

---

## Context

The Sprint 1 data model proposed two models for authentication state: `Session` (tracks login sessions with device info) and `RefreshToken` (tracks token rotation and theft detection). Both store `userId`, `isRevoked`, and `expiresAt`. Both are created on login and revoked on logout.

During implementation planning, a question was raised: is the Session model truly required, or is it architectural over-design for a gym management system?

---

## Analysis

### Confirmed Requirements

| Requirement | Satisfied by RefreshToken alone? |
|-------------|----------------------------------|
| Email/Password login + JWT | Yes — create RefreshToken |
| Token refresh with rotation | Yes — `rotate()` replaces old, creates new in same `family` |
| Token theft detection | Yes — reuse triggers `revokeFamily()` |
| Logout (single device) | Yes — `isRevoked: true` on one token |
| Logout all devices | Yes — `revokeAllForUser(userId)` |
| Password reset | Yes — PasswordResetToken handles email link |
| OTP verification | Yes — OTP model handles codes |
| Social auth (Google/Facebook) | Yes — same login flow, create RefreshToken |
| BR-AUD-004 (max 3 concurrent logins) | Yes — count non-revoked, non-expired RefreshTokens per userId |

### Session Model's Unique Contribution

Only one field: `deviceInfo` (`{ userAgent, ip, platform }`). Everything else — `userId`, `refreshToken` field, `isRevoked`, `expiresAt`, TTL — already exists in RefreshToken.

### YAGNI Assessment

The Session model exists because:
1. `DATABASE.md` §2.1 listed it as a collection (architectural design)
2. BR-AUD-004 uses the word "session" in its description (conceptual, not implementation mandate)
3. It follows a generic "sessions + tokens" auth pattern common in enterprise apps

No GymPro-specific feature requires a separate Session model. Device management UI, session history dashboards, and per-device force-logout are not planned features.

### Maintenance Cost of Dual Models

| Operation | With Session + RefreshToken | With RefreshToken only |
|-----------|---------------------------|----------------------|
| Login | 2 DB writes | 1 DB write |
| Logout | 2 DB writes | 1 DB write |
| Refresh | 2 DB writes (Session.update + Token.rotate) | 1 DB write |
| BR-AUD-004 check | Count sessions OR risk sync drift | 1 query |
| TTL indexes | 2 | 1 |
| Models | 2 files | 1 file |
| Sync risk | Session.refreshToken must match RefreshToken.token | None |

---

## Alternatives Considered

### Option A: Keep Both (Rejected)

Keep Session and RefreshToken as separate models. Enforce 1:1 mapping at the service layer.

**Rejected because:** YAGNI. No feature needs the separation. Every auth operation requires 2 DB writes with sync risk. Maintenance cost exceeds benefit.

### Option B: Keep Session, Remove RefreshToken (Rejected)

Store family and rotation logic on Session.

**Rejected because:** RefreshToken has theft detection logic (`revokeFamily`) that is well-scoped. Session mixing device tracking with cryptographic rotation violates single responsibility. The family-based rotation is the cleaner abstraction to extend.

### Option C: Remove Session (Accepted)

RefreshToken absorbs `deviceInfo`. All auth state in one model.

**Accepted because:** Simplest model that satisfies all requirements. One DB write per auth operation. YAGNI respected. If device management is needed later, `deviceInfo` is already captured.

---

## Decision

**Remove the `Session` model from the project architecture.**

RefreshToken becomes the single authentication state model with the following extensions:

1. **Add `deviceInfo` field:** `{ userAgent: String, ip: String, platform: String }` — optional object captured on login.
2. **Add `countActiveByUser(userId)` static:** Returns count of non-revoked, non-expired RefreshTokens for a user. Used to enforce BR-AUD-004.
3. **BR-AUD-004 enforcement:** On login, count active tokens. If ≥ 3, invalidate the oldest (by `createdAt`), create new. Implemented in `authService.js`, not in the model.

---

## Business Justification

- Reduces code surface that must be tested and maintained for a given auth operation by 50% (1 write vs 2).
- BR-AUD-004 compliance is simpler with a single model: count tokens, not count sessions.
- No business requirement exists for device management, session history, or per-device force-logout.
- If these features become required, `deviceInfo` is already stored — implementing them requires querying and filtering, not migrating data from a separate collection.

---

## Technical Justification

- Eliminates a synchronization point: `Session.refreshToken` no longer needs to match `RefreshToken.token`.
- Reduces TTL indexes from 2 to 1.
- Database writes per login flow drop from 2 to 1.
- RefreshToken's existing statics (`rotate`, `revokeFamily`, `revokeAllForUser`) remain unchanged. One new static (`countActiveByUser`) added with ~3 lines.
- No migration needed: the Session model was never implemented. No collection to drop, no data to migrate.

## Future Extensibility

- **Device management UI:** Add `GET /auth/devices` endpoint that queries `RefreshToken.find({ userId, isRevoked: false }, 'deviceInfo createdAt')`.
- **Per-device logout:** `PATCH /auth/devices/:tokenId/logout` → `RefreshToken.findByIdAndUpdate(tokenId, { isRevoked: true })`.
- **Device fingerprinting:** Add `deviceFingerprint` to `deviceInfo` object. No schema migration — Mixed/Object type.
- **Session analytics:** Aggregate `RefreshToken` by userId, platform, or ip. No new model needed.

# ADR-001: MongoDB over PostgreSQL

- **Status**: Accepted
- **Date**: 2024-06-01
- **Deciders**: Technical Lead, Architects

## Context

The gym management system requires a flexible document schema to handle varied data structures across membership cycles, workout plans, booking slots, and user profiles. These entities often have varying fields depending on membership tier, plan type, or service category. Geospatial queries are needed for gym location search and proximity-based features. The team has existing MongoDB experience and prefers a document-oriented approach. PostgreSQL's rigid schema would require complex migrations for each structural change and extensive EAV (Entity-Attribute-Value) patterns to achieve comparable flexibility.

## Decision

Use MongoDB as the primary database with Mongoose ODM for schema validation and data modeling. Apply Mongoose schemas with strict mode for data consistency where needed.

## Consequences

- (+) Schema flexibility enables fast iteration on membership plans, workout templates, and booking configurations without migrations.
- (+) Native JSON storage matches the API layer's data format, reducing transformation overhead.
- (+) Geospatial queries ($near, $geoWithin) are first-class citizens for gym location features.
- (+) MongoDB 4.0+ provides multi-document transactions for critical operations (payments, bookings).
- (-) Eventual consistency defaults require careful read-concern configuration for financial operations.
- (-) Reporting and analytics tooling is less mature than PostgreSQL (fewer native BI connectors).
- (-) Join operations are less performant than relational databases; prefer embedding or denormalization.

## Compliance

All new features must define a Mongoose schema with appropriate indexes. Schema changes must be reviewed for read/write pattern impact. Transactions must be used for operations involving payments or booking state changes.
